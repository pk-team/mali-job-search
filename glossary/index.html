Buzzword deflator

Scary words, ordinary engineering decisions.

A useful definition says what problem the concept solves, what it costs, where it sits in a system, and what an application developer actually does with it.

Answer pattern: “X is … Teams choose it when … The trade-off is … In this project, I used it by …” If Mali has only practised it, say “in my learning project”—never imply production experience.
Optionality

The number and quality of useful future choices available, combined with the ability to recognize and take them. Learning increases optionality when it produces judgement, evidence, relationships, or capabilities that transfer to more than one path. An option also has costs: time, lock-in, reputation, money, and alternatives it may close.

Systems thinking

Understanding a piece of software as part of a larger network of people, goals, incentives, information, delays, dependencies, risks, and feedback. It asks not only whether code works, but why the system exists, who benefits, who bears failure, and what changes elsewhere when one part changes.

Transport / protocol

The agreed way data moves between parts of a system. It defines the shape and rules of the conversation; it is not the business purpose of the application. Good application boundaries keep much of the UI and domain logic independent of the chosen transport.

REST API

An HTTP-based style that exposes resources through familiar operations and status codes. It is easy to inspect and broadly supported. Teams still need conventions for versioning, errors, filtering, and generated client types.

gRPC

A remote-call system commonly using Protocol Buffers for a strongly defined contract and compact binary messages. It can suit internal service-to-service communication and streaming. The application developer normally generates a client from the contract, wraps it behind an interface, and handles timeouts and failures; she is not expected to invent the protocol.

GraphQL

An API query language and runtime where a client requests the fields it needs through a typed schema. It can make complex frontend data needs expressive, while adding schema, caching, authorization, and query-cost concerns on the server.

Interface / abstraction

A small contract describing what a component can do without tying callers to one implementation. For example, a UI can call an IOrdersGateway whether the gateway uses REST, gRPC, or an in-memory fake. The abstraction is valuable when it reflects a real boundary, not when added mechanically.

Dependency injection

Giving an object its collaborators from the outside instead of constructing them internally. This makes dependencies visible and allows implementations to be replaced for tests or different environments. The container is wiring; the important idea is dependency direction.

Frontend

The part of the system through which a person perceives and controls the product. It includes interaction design, accessibility, state, validation, error recovery, API integration, performance, and visual implementation—not merely decoration.

Backend

Server-side code and infrastructure that enforce rules, store data, integrate systems, authenticate requests, and coordinate work. Calling an API from a frontend is backend integration experience, but it is not evidence of owning that backend.

Razor / Blazor

Razor is .NET's templating syntax. Blazor uses Razor components to build interactive web interfaces with C#. Blazor can serve internal or public applications; suitability depends on interaction needs, performance constraints, team skills, and delivery model—not a universal internal-versus-public rule.

ORM / Entity Framework Core

An object-relational mapper translates between application objects and relational database operations. It removes repetitive data-access work but does not remove the need to understand queries, transactions, indexes, migrations, and data shape.

Container / Docker

A repeatable package for an application and its runtime dependencies. Containers reduce environment differences and help local setup and deployment, but they do not automatically provide orchestration, security, monitoring, or a good release process.

CI/CD

Automation that checks changes and prepares or performs releases. CI builds and tests every change; delivery/deployment moves verified versions toward users. The real value is fast feedback and repeatability, not the particular YAML service.

Automated test

Executable evidence that a behavior still works. Unit tests isolate a small rule, integration tests check real boundaries, and end-to-end tests exercise a user path. Choose the cheapest level that catches the important failure.

Accessibility

Designing so people with different vision, movement, hearing, and cognition can use the interface. For frontend work this includes semantic HTML, keyboard operation, focus, labels, contrast, clear errors, and testing with assistive technology.
